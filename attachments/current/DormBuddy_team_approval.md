# DormBuddy — рабочая концепция проекта

**Дата:** 2 ноября 2026 года  
**Дисциплина:** «Практикум программирования на Python»  
**Статус:** предложение для обсуждения; тема, состав MVP и распределение ответственности требуют согласования.

## 1. Что делаем

DormBuddy — веб-сервис для студентов, переезжающих в Москву: помогает найти совместимого соседа, параллельно подобрать жильё и освоиться после переезда с контекстным AI-помощником.

**Product Vision:** дать студенту единое пространство для поиска человека, места для жизни и решения бытовых вопросов. Начать можно с любой задачи: наличие соседа не требуется для поиска квартиры, а найденная квартира — для подбора соседа.

Это учебный программный проект. На первом этапе результатом должен стать работающий сервис с собственной логикой, базой данных и законченными пользовательскими сценариями. Рыночные оценки, монетизация и коммерческие партнёрства не определяют объём MVP.

## 2. Для кого и какую проблему решаем

Основная аудитория — абитуриенты и студенты первых курсов, переезжающие учиться в Москву. Вторичная — студенты, меняющие жильё или соседа.

Рабочие персоны для проектирования, а не результаты проведённого исследования:

| Персона | Ситуация | Что нужно получить |
| --- | --- | --- |
| Первокурсник с местом в общежитии | Знает вуз и общежитие, не знает будущих соседей | Найти потенциального соседа с похожими бытовыми привычками |
| Студент без общежития | Ищет аренду с ограниченным бюджетом | Параллельно смотреть жильё и людей для совместной аренды |
| Студент после переезда | Жильё уже найдено, самостоятельный быт ещё не организован | Получать помощь с переездом, расходами и повседневными задачами |

Проблема: поиск жилья, поиск соседа и адаптация обычно требуют разных инструментов. При этом подходящий бюджет ещё не означает совместимость в быту. Гипотеза проекта — объяснимый подбор и общий контекст пользователя сделают этот процесс удобнее. Проверка гипотезы — отдельная задача; спрос и эффективность пока не считаем доказанными.

## 3. Центральная функция — объяснимый подбор соседей

Пользователь заполняет анкету. Сервис сначала проверяет обязательные условия, затем ранжирует допустимых кандидатов по бытовым предпочтениям. На карточке видны оценка совместимости и конкретные совпадения и расхождения.

### Обязательные условия

- Совместимость бюджетных диапазонов для совместной аренды.
- Вуз и общежитие, когда пользователь включил соответствующий режим и ограничение.
- Допустимость курения и проживания с животными.
- Другие условия только при явном выборе пользователя как обязательных.

Проверка двусторонняя: кандидат должен удовлетворять ограничениям пользователя, а пользователь — ограничениям кандидата. Вуз не является обязательным фильтром для всей аудитории. Бюджет означает долю расходов одного человека на жильё в месяц; дополнительные расходы показываются отдельно.

### Предпочтения

Режим сна, частота уборки, отношение к гостям, допустимый шум, готовка и общительность. Для MVP используем понятные категории и шкалы с заранее описанными правилами сравнения.

**Предлагаемый алгоритм для согласования:**

1. Исключить себя, неподходящие профили и кандидатов с конфликтом обязательных условий.
2. Для каждого заполненного с обеих сторон предпочтения вычислить сходство `s_i` от 0 до 1.
3. Рассчитать направленную оценку `S(A→B) = 100 × sum(w_Ai × s_i) / sum(w_Ai)` по сопоставимым признакам. Веса на старте равные; пользовательские веса — возможное развитие.
4. Для пары использовать среднее двух направленных оценок. Показать полноту сравнения: сколько признаков удалось сопоставить.
5. Отсортировать по оценке; при равенстве использовать стабильный порядок по идентификатору.
6. Сформировать объяснение из тех же правил: основные совпадения и существенные расхождения.

Неизвестное значение не считаем совпадением. Если неизвестен признак, необходимый для обязательного условия, профиль не попадает в подтверждённо подходящие кандидаты до заполнения. Если общих предпочтений нет, показываем «недостаточно данных», а не процент.

Оценка — индекс сходства анкет, а не вероятность успешного совместного проживания. Объяснение формируется программно; LLM не вычисляет и не меняет результат matching.

## 4. Пользовательские сценарии

### Соседи

Регистрация → профиль → анкета → лента рекомендаций → просмотр совместимости → Like / Skip. Взаимный Like создаёт один Mutual Match. Повторный запрос не создаёт дубликат. После match пользователи видят общие понравившиеся объявления. Пользовательский чат пока не входит в MVP.

### Жильё

Отдельная вкладка → фильтры → карточка квартиры или комнаты → избранное. Можно пользоваться независимо от поиска соседей. Фильтры MVP: стоимость доли аренды, район или метро, тип жилья, допустимость животных и курения. Для объявлений с общей ценой явно показываем число жильцов и расчёт доли; не смешиваем её с ценой всей квартиры.

В MVP используется собственная демонстрационная база Москвы. Объявления явно помечены как учебные, без обещания реальной доступности. Реальные API добавляем после проверки доступности и условий использования; готовность проекта от них не зависит.

### Общежитие

Пользователь выбирает вуз и общежитие → получает потенциальных соседей в этом контексте → сравнивает бытовые привычки → ставит Like. Сервис помогает познакомиться с потенциальным соседом; фактическое заселение и распределение мест остаются за вузом. Интеграции с администрацией общежитий нет.

### AI Buddy

Помощник ведёт диалог и использует доступный контекст: вуз, район или общежитие, бюджет, интересы и этап переезда. Основные сценарии: чек-лист переезда, первые дни в общежитии, организация быта, планирование расходов и досуга.

Примеры: «Что купить в общежитие в первый день?», «Помоги распределить месячный бюджет с учётом аренды», «Составь план первой недели после переезда».

Предлагаем хранить историю диалога и позволить пользователю уточнять запрос. Передаём LLM только необходимый контекст текущего пользователя. Профили других людей, контакты и секреты сервера в запрос не включаем. Актуальные цены, события и маршруты без внешнего источника не представляем как проверенные. При недоступности LLM остальные функции продолжают работать, а помощник сообщает об ошибке и позволяет повторить запрос.

## 5. Границы MVP

| Входит в первую версию | Граница реализации |
| --- | --- |
| Регистрация и авторизация | Учётная запись, вход, доступ только к собственным изменениям |
| Профиль и анкета | Основные данные, режим аренды/общежития, бюджет, привычки |
| Matching | Двусторонние ограничения, оценка, объяснение и ранжирование |
| Like / Skip / Mutual Match | Сохранение действий, отсутствие дубликатов match |
| Общежитие | Справочники вузов/общежитий и подбор внутри выбранного контекста |
| Жильё | Параллельная лента, фильтры и избранное на тестовых данных Москвы |
| Общие понравившиеся варианты | Пересечение избранного только для пары с mutual match |
| AI Buddy | Диалог через LLM API с контекстом пользователя и обработкой ошибок |
| Демонстрация | Воспроизводимое наполнение БД и сквозные сценарии в интерфейсе |

**После MVP:** реальные API жилья, рекламная монетизация, встроенный чат, верификация через вуз, интеграции с общежитиями, совместные покупки и бюджет, расписание уборки, мобильное приложение, другие города. Время до вуза и маршруты — расширение при наличии подходящего источника; заранее подготовленную оценку следует явно подписывать.

При нехватке времени сначала упрощаем оформление интерфейса, расширенные фильтры и внешние интеграции. Если меняем центральные сценарии, сначала обсуждаем это между собой и согласуем новый объём с преподавателем.

## 6. Архитектура и данные

**Предлагаемый стек:** Python, FastAPI, SQLAlchemy, PostgreSQL, LLM API. Архитектура — модульный монолит с единым приложением и БД. Для демонстрации нужен простой веб-интерфейс; конкретный frontend выберем отдельно.

Модули: `Auth`, `Profiles`, `Matching`, `Swipes & Matches`, `Housing`, `Dormitories`, `Buddy`. Правила подбора отделяем от HTTP-обработчиков и вызовов LLM, чтобы их можно было объяснить и проверить независимо.

| Сущности | Назначение и связи |
| --- | --- |
| User, Profile, Preferences | Учётная запись и связанные с ней профиль и анкета |
| University, Dormitory | Вуз имеет несколько общежитий; профиль ссылается на выбранные записи |
| Swipe, Match | Направленное действие пользователя и уникальная неупорядоченная пара при взаимной симпатии |
| HousingListing, Favorite | Объявление и связь пользователя с избранным; пара пользователь–объявление уникальна |
| BuddyConversation, BuddyMessage | Диалог принадлежит пользователю и содержит сообщения |

Анкеты и избранное сохраняются в БД. Score на старте вычисляется по текущим данным, поэтому отдельное хранилище рекомендаций не обязательно. Изменение анкеты должно влиять на следующую выдачу.

### Предлагаемые требования к качеству

- Пароли хранятся как стойкие хеши; API проверяет авторизацию и права доступа.
- Ключи LLM и настройки БД вынесены из репозитория и клиентского кода.
- Входные данные валидируются; ошибки имеют понятные ответы.
- Миграции и скрипт заполнения позволяют воспроизвести демонстрационную БД.
- Matching детерминирован при одинаковых данных; ошибки LLM не нарушают работу лент.
- Для обычной выдачи на демобазе предлагаем целевое время до 1 секунды на согласованной машине; вызовы LLM измеряются отдельно. Это целевой показатель, а не достигнутый результат.

## 7. Что покажем на защите и как проверим

1. Два тестовых пользователя создают профили и анкеты.
2. Конфликт обязательного условия исключает кандидата; у допустимого кандидата видны score и причины.
3. Изменение бытового предпочтения меняет оценку ожидаемым образом.
4. Первый Like не создаёт match, ответный Like создаёт его ровно один раз.
5. В параллельной ленте работают фильтры и избранное; у пары доступны общие варианты.
6. Переключение в режим общежития ограничивает круг кандидатов выбранным контекстом.
7. Buddy отвечает с учётом профиля; демонстрируется и обработка недоступности провайдера.

При реализации нужны содержательные проверки: двусторонние ограничения, неполная анкета и отсутствие деления на ноль; диапазон score; повторные и одновременные лайки; доступ к чужим данным; фильтры и пересечение избранного; отказ LLM. Подготовленные тестовые пары должны включать как совпадения, так и конфликты.

## 8. Организация работы

Предлагаем спринты по 1–2 недели. Точные сроки и число спринтов определим после подтверждения дедлайна и доступности участников.

| Этап | Проверяемый результат |
| --- | --- |
| Согласование | Приняты тема, MVP, стек и ответственность участников |
| Проектирование | Product Vision, персоны, User Stories с критериями приёмки и проверкой INVEST, Story Map, CJM, C4 Context, схема БД, нефункциональные требования, backlog |
| Первый рабочий сценарий | Вход → анкета → сохранение в БД → рекомендации с объяснением |
| Расширение MVP | Взаимные лайки, общежития, жильё, избранное и общие варианты |
| Интеграция и защита | AI Buddy, проверки, обработка ошибок, воспроизводимый запуск и демо |

Предлагаем разделить работу на четыре направления. Ответственных определим вместе:

| Направление | Ответственность |
| --- | --- |
| Backend и данные | Авторизация, модели БД, миграции, справочники, согласование API |
| Подбор и взаимодействия | Анкета, алгоритм, объяснения, Like/Skip и mutual match |
| Жильё и интерфейс | Ленты, фильтры, карточки, избранное, связка интерфейса с API |
| Buddy и интеграция | LLM-контекст, история диалога, обработка отказов, сборка сквозного демо |

Если работаем втроём, объединяем направления после оценки нагрузки. Документируем и проверяем свои части; интеграцию, ревью и подготовку защиты делаем вместе. Ответственных и сроки зафиксируем перед первым спринтом.

- [ ] Сохраняем независимые ленты «Соседи» и «Жильё».

- [ ] Подтверждаем состав MVP и исключения из него.

## Основание и статус требований

В основу концепции из `DormBuddy_Овчинников_v2.pdf` и `DormBuddy_Овчинников_учебный.pdf` внесли уточнения: Москва, параллельные ленты, центральный сценарий общежития, объяснимый matching со свайпами, полноценный Buddy, тестовая база при отсутствии API.

Ориентиры курса восстановлены из предыдущего обсуждения: нетривиальный сервис с понятной ЦА и ключевой функцией, Python/FastAPI/SQLAlchemy/БД, объяснимая архитектура, проектные артефакты и защита через демо. Исходный лист критериев Овчинникова в доступных материалах не найден; это не дословная рубрика и не подтверждение уже полученного согласования. Формулу score, требования к качеству, этапы и разделение работы выше пока рассматриваем как предложения и уточняем перед реализацией.
